# 第二大脑压力分担模型

> 工作札记。自资产领域札记仓（quanttide-essay-of-asset-management）移入，资产中文名按《量潮标准范畴》口径更正。

## 陈述型记忆九宫格

陈述型记忆回答组织「知道什么」的问题，按类型维度（事件类、语义类、自我类）与时间维度（过去、现在、未来）交织为九宫格。

```text
                journal（日志）——驱动整个循环
                ┌─────────────────────────────┐
                │        语义类     自我类     │
                │  事件类  │         │         │
                ├─────────┼─────────┼─────────┤
   过去         │  report │ library │ history │  ← 回顾+认同压力
                │  （报告）│ （图书馆）│ （历史）  │
               ─│─────────│─────────│─────────│─
   现在         │ journal │ profile │ brochure│  ← 执行+不确定压力
                │  （日志）│ （档案）  │（宣传册） │
               ─│─────────│─────────│─────────│─
   未来         │ roadmap │ insight │intention│  ← 方向压力
                │（路线图）│ （洞察）  │（愿景）  │
                ├─────────┴─────────┴─────────┤
                │          AI 执行层           │
                └─────────────────────────────┘
```

### 第一组：未来 — 方向压力

回答「往哪走」。压力源是方向不明确、边界不清楚、判断没依据。

**intention（愿景）— 自我类**
- 回答的问题：为什么做？什么不做？
- 内容特征：「不做」比「要做」更重要。每一句「我们不做 X」都是帮人类省掉一次纠结。
- 维护方式：遇到决策先问「这事在我们的意图范围内吗？」

**insight（洞察）— 语义类**
- 回答的问题：看到了什么？怎么判断？
- 内容特征：记录判断逻辑，而非结论。结论会过时，判断逻辑不会。
- 维护方式：做完一件事后，把「我发现了什么规律」写在这里。

**roadmap（路线图）— 事件类**
- 回答的问题：去哪里？先去哪再去哪？
- 内容特征：可执行的步骤链，每一步应该是「明天可以开始做的事」。
- 维护方式：把目标拆成 1-2 天内可完成的步骤，完成即划掉。

### 第二组：现在 — 执行与不确定压力

回答「从哪出发」。压力源是事情太多做不完、外部变化太快、信息不一致。

**journal（日志）— 事件类**
- 回答的问题：当前在做什么？在想什么？
- 内容特征：零门槛的原始记录，整个体系的驱动点。
- 维护方式：有想法就记，定期回顾，提炼有持续价值的内容到对应仓库。

**profile（档案）— 语义类**
- 回答的问题：当前是什么状态？有什么事实依据？
- 内容特征：当前状态的事实快照，含可验证数据和明确定义。
- 维护方式：以数据（JSON/YAML）为主，关键数据定期更新。

**brochure（宣传册）— 自我类**
- 回答的问题：对外怎么说？
- 内容特征：对外版本的事实和故事。profile 是对内的全部事实，brochure 是对外的精选事实。
- 维护方式：profile 更新后检查 brochure 是否需要同步。

### 第三组：过去 — 回顾与认同压力

回答「走过什么路」。压力源是不确定自己做对了没有、不知如何证明、怕重复踩坑。

**history（历史）— 自我类**
- 回答的问题：走过什么路？踩过什么坑？
- 内容特征：关键事件时间线 + 经验教训，不记流水账。
- 维护方式：定期回顾日志，将有长期价值的事件提炼至此。

**library（图书馆）— 语义类**
- 回答的问题：外部参考了什么？有什么依据？
- 内容特征：外部资料的索引和提炼。价值不在于收藏多少，在于有多少被引用过。
- 维护方式：读到的资料记于此，写清楚「为什么值得记」。

**report（报告）— 事件类**
- 回答的问题：做得怎么样？有什么成果？
- 内容特征：结构化的事实汇总，含数据、趋势、对比。
- 维护方式：定期从 journal 和 profile 提取数据，生成结构化报告。

### 流转关系

```text
journal（日志）——所有想法的入口
    │
    ├──→ 日常执行 → profile 更新当前状态
    │
    ├──→ 发现问题 → intention 调整边界
    │              → insight 记录判断
    │              → roadmap 新增步骤
    │
    ├──→ 完成事项 → report 生成总结
    │              → history 沉淀经验
    │
    ├──→ 外部参考 → library 收录资料
    │
    └──→ 对外输出 → brochure 统一口径
```

## 程序型记忆九宫格

程序型记忆回答组织「怎么做事」的问题，按约束力层次（宪法、法律、法理）与消费对象（人类友好、AI友好、规则引擎友好）交织为九宫格。

```text
                 人类友好          AI友好          规则引擎友好
                  (可读性)        (可解析)          (可执行)
                 ┌──────────────┬──────────────┬──────────────┐
    宪法         │  Bylaw       │ Specification │  Toolkit     │
   （最高约束）    │  章程        │  工程标准      │  工具箱       │
                 ├──────────────┼──────────────┼──────────────┤
    法律         │  Handbook    │  Gallery      │  Platform    │
   （中等约束）    │  手册        │  案例         │  平台         │
                 ├──────────────┼──────────────┼──────────────┤
    法理         │  Tutorial    │  Essay        │  Laboratory  │
   （低约束）      │  教程        │  论文         │  实验室       │
                 └──────────────┴──────────────┴──────────────┘
```

### 第一组：宪法层 — 治理压力

回答「底线是什么」。压力源是权责不清、标准缺失、重复劳动。

**Bylaw（章程）— 人类友好**
- 回答的问题：谁做什么？什么能做、什么不能做？
- 压力场景：决策时不知道谁有权拍板；跨团队协作时边界模糊；遇到争议没有裁决依据。
- 内容特征：治理规则文档，定义宗旨、权力范围和运作原则。所有人必须遵守的基本法。
- 维护方式：变更须经审议，保证九宫格结构的一致性与完整性。

**Specification（工程标准）— AI友好**
- 回答的问题：什么是正确的？怎么判断好坏？
- 压力场景：AI 生成内容格式不统一、质量参差不齐；团队输出风格不一致；缺乏可量化的质量门禁。
- 内容特征：规范化工程实践的文档标准，供 AI 系统解析和验证。定义「什么是正确的」。
- 维护方式：在实践中发现问题后迭代完善，提供正确和错误的对比示例。

**Toolkit（工具箱）— 规则引擎友好**
- 回答的问题：怎么自动化？怎么减少手工？
- 压力场景：治理规则靠人记、靠人查、靠人执行，遗漏和出错频繁；重复劳动消耗大量时间。
- 内容特征：封装治理规则的自动化工具集，供 CI/CD 和规则引擎直接调用。
- 维护方式：随规格标准更新同步迭代，保持工具与规范一致。

### 第二组：法律层 — 操作压力

回答「具体怎么做」。压力源是流程不明确、经验难复用、协同低效。

**Handbook（手册）— 人类友好**
- 回答的问题：这个任务具体怎么做？标准步骤是什么？
- 压力场景：新人上手慢，老员工操作靠口口相传；同一个流程不同人做出来不一样；出了错不知道哪个环节有问题。
- 内容特征：针对具体岗位或业务流程的标准化操作指导（SOP），只说怎么做，不解释为什么。
- 维护方式：引用规范来源，提供版本化链接，更新时同步更新版本号。

**Gallery（案例）— AI友好**
- 回答的问题：以前类似情况怎么处理的？有什么可以参考？
- 压力场景：遇到新问题不知道从哪入手；知道有先例但找不到细节；不同项目各自摸索，经验无法复用。
- 内容特征：结构化的案例库，供 AI 参考和类比推理。
- 维护方式：完成一个阶段后整理案例，标注背景、方案、效果和教训。

**Platform（平台）— 规则引擎友好**
- 回答的问题：流程怎么跑通？怎么让系统自动运转？
- 压力场景：审批靠邮件、沟通靠群聊、进度靠追问；信息散落在各个工具里，找不到统一入口。
- 内容特征：承载组织运营、协同办公和业务流转的数字空间，将流程自动化。
- 维护方式：持续集成职能域能力，逐步覆盖业务线和职能线。

### 第三组：法理层 — 认知压力

回答「为什么这么做」。压力源是知识门槛高、方法论缺失、理论难落地。

**Tutorial（教程）— 人类友好**
- 回答的问题：这个知识怎么理解？怎么学会？
- 压力场景：概念太抽象看不懂；文档只讲规范不讲原理；想学但不知道从哪开始。
- 内容特征：面向人的学习材料，帮助理解和掌握操作方法，重视让人理解。
- 维护方式：剥离当下的故事性，提炼程序性知识，持续验证可执行性。

**Essay（论文）— AI友好**
- 回答的问题：背后是什么方法论？有什么深层规律？
- 压力场景：只知道怎么做，不知道为什么这么做；遇到新问题缺乏判断框架；AI 缺乏足够的方法论上下文。
- 内容特征：关于方法论的总结与思考，指导 AI 的上下文构建，偏准学术写作。
- 维护方式：围绕现有概念进行整合，逐步交给 AI 接管。

**Laboratory（实验室）— 规则引擎友好**
- 回答的问题：这个方案怎么实现？有没有可运行的参考？
- 压力场景：理论说得通但不知道怎么编码实现；文档示例与实际情况脱节；重复造轮子。
- 内容特征：可执行的代码示例，演示具体实现方式，通常是小型独立项目。
- 维护方式：遵循主要语言的项目规范，随技术栈升级同步更新。

### 纵向压力分流

```text
宪法层     定义「什么能做」→ 消除方向性焦虑
  ↑
法律层     指导「怎么做」  → 消除操作性焦虑
  ↑
法理层     解释「为什么」  → 消除认知性焦虑
```

越往上约束力越强，压力也越根本。宪法层解决的是「要不要做」的根本问题，法律层解决「怎么做」的操作问题，法理层解决「为什么这么做」的理解问题。三层叠加，覆盖从决策到执行再到理解的完整压力链。

## Context（上下文）

Context 是所有九宫格资产的默认入口，不占九宫格位置。

- **定位：** 用户从日常工作中感知到某个模式或疑问后，自然地进入 Context 记录观察与约束。这些语境信息成为后续未来格子的共同起点。
- **压力场景：** 想法碎片化、无从分类；不确定该归到哪个格子时，先放 Context。
- **维护方式：** 不需要结构化，记录原始观察和约束，后续提炼到对应格子。

## Archive（归档）

Archive 用于备份两类九宫格中所有格子的过时文件，不占九宫格位置。

- **定位：** 确保组织知识的持久化存储与可追溯性。
- **压力场景：** 过时文件堆积、当前信息混淆；担心删除后无法找回。
- **维护方式：** 定期将不再活跃的文件移至 Archive，保持九宫格当前的整洁。

## 核心结论

压力不是被「解决」的，是被这个系统分流了。每一组承接一部分压力，剩下的交给下一组或 AI。日志是驱动点，AI 是执行层。
